# v0.1 specification

## Purpose

v0.1 should prove the architecture with a narrow but genuinely useful end-to-end product. It is not a documentation-only milestone and not a broad editor.

The defining vertical slice is:

```text
Android phone
-> Wi-Fi upload/share
-> Inbox
-> local asset ingest
-> draft project
-> hook_overlay template
-> fast preview
-> mobile approval
-> final 1080x1920 render
-> QC
-> export MP4 + sidecar metadata
```

Everything in v0.1 should strengthen this path or make it extensible to the already identified non-voiced formats.

## User story

1. The user finds a short source clip on the phone or already has it in the gallery/files.
2. The user shares/uploads the clip to Content Forge over Wi-Fi and optionally includes a source URL/note.
3. The desktop stores the asset, hashes it, probes it, creates a thumbnail/proxy, and creates a draft project.
4. The project is prepared using `hook_overlay` or another initial template.
5. The user enters a hook or asks the optional LLM provider for suggestions.
6. The system renders a low-resolution preview.
7. The user approves or edits the hook/crop from phone.
8. The desktop renders the final Short using NVENC when available, with software fallback.
9. QC verifies basic output correctness and surfaces warnings.
10. The export directory contains the MP4 plus a project/render metadata sidecar.

## Required runtime capabilities

### Core models

At minimum:

```text
Project
Asset
AssetRef
SourceRecord
Variant
Scene
Overlay
AudioTrack
TemplateRef
OutputProfile
ReviewTask
Job
RenderManifest
QCResult
```

All persisted canonical models carry a schema version where migration may matter.

### Persistence

SQLite is the first canonical application database for:

- asset metadata;
- source/provenance records;
- projects;
- variants;
- review tasks;
- jobs;
- render/export records.

Large media and generated files remain filesystem assets referenced from metadata.

### Asset store

Requirements:

- SHA-256 identity;
- deduplicate identical files;
- immutable original bytes after ingest;
- file type/media metadata;
- ffprobe integration for video/audio;
- thumbnails;
- proxy generation;
- source URL/creator/notes attached separately.

### Timeline/render plan

The normalized timeline must support enough primitives for initial templates:

```text
image/video scenes
explicit duration/trim
cover/contain
crop/focus rectangle
text overlay
image overlay
z-order
simple slow zoom/pan
basic transition
original audio
music audio
```

### Render backend

Requirements:

- FFmpeg/ffprobe executable discovery/configuration;
- capability probe;
- H.264 encode;
- NVENC path when available;
- CPU fallback;
- 1080x1920 final profile;
- 540x960 preview profile;
- structured command execution and errors;
- cancellation where practical;
- command/plan recorded for debugging/reproducibility.

### Static raster backend

Pillow supports wrapped/rich static cards and overlays. `hook_overlay` can use a simple text implementation initially, but the architecture must permit rasterized static components.

### API

FastAPI endpoints should eventually cover at least:

```text
health/status
pair/auth (minimal local pairing)
assets ingest/upload
URL/note ingest
inbox/project list
project detail/update
review task list/resolve
preview request/status
final render request/status
artifact/download/preview access
worker/job status
```

Exact REST paths are an implementation detail to be frozen in API PRs.

### PWA

The mobile UI must support:

- installation/home-screen use;
- file upload;
- share target if reliable on target Android/browser;
- Inbox list;
- project preview;
- hook edit/selection;
- simple crop/fit confirmation where needed;
- review queue;
- trigger preview/final render;
- see render/job status;
- access completed export/metadata summary.

Desktop may use the same frontend with a wider layout.

## Initial templates required by v0.1

The implementation may land them over several PRs, but v0.1 should include:

### `hook_overlay`

Full-screen media + top hook.

Required first because it provides the smallest vertical slice.

### `hook_topbar`

Dedicated header band + media.

### `social_post`

Profile/caption header + media slot.

### `meme_white_header`

Simple meme text area + media.

### `content_frame`

Header/profile/footer/frame + main media slot, suitable for anime/other framed clips.

### `art_story`

One or more images with motion, credit, and optional reaction/comment components.

### `panel_sequence`

Ordered panel images with readable timing, motion/transitions, and music.

### `sync_stack`

N synchronized instances of one source with hook/premise and optional reaction overlay.

These do not each require unique workflow code if existing scene/components suffice.

## LLM support

v0.1 includes an optional `LLMProvider` implementation around `chatgpt-web-adapter` for:

- hook suggestions;
- title/description suggestions;
- translation/localization;
- content-kind/template suggestions;
- generic text cleanup helper.

Requirements:

- no LLM call required to render an explicit project;
- suggestions are persisted separately from accepted values;
- provider failure has a clean manual fallback;
- secrets/session data remain outside project manifests and Git.

## Variants

v0.1 should support the data model and practical rendering of language variants, at least for simple text fields.

One master project can share:

- source assets;
- timing;
- most scene geometry;

while variant data changes:

- hook;
- title;
- description;
- hashtags;
- optional font/style overrides.

EN/JA/KO are useful test cases for typography architecture, but production translations are not CI fixtures.

## Review tasks required by v0.1

At minimum the UI/domain should support:

```text
text_input / edit_hook
choose_option
confirm_crop_or_fit
reorder_images
choose_template
choose_reaction (optional)
choose_music (optional)
confirm_credit
approve_preview
```

The review system must be extensible to OCR/speaker/voice tasks later without new project states.

## Project statuses

Required coarse statuses:

```text
INBOX
DRAFT
PREPARED
NEEDS_REVIEW
READY
RENDERING
QC
DONE
```

Failed jobs are represented independently, with the project left in the last meaningful recoverable state.

## Job queue

Use SQLite-backed persistent jobs; no external broker.

Required properties:

- claim one job safely;
- status: queued/running/succeeded/failed/cancelled as needed;
- attempts and error record;
- restart-safe;
- idempotent or deduplicated job creation for expensive deterministic tasks where practical.

## QC required by v0.1

Blocking checks:

- output exists and probes successfully;
- dimensions match profile;
- non-zero sensible duration;
- required sources/assets present;
- render process succeeded;
- text layout did not fail/overflow beyond configured policy.

Warnings:

- safe-zone overlap;
- unexpected missing audio when source normally has audio;
- audio peak/loudness sanity;
- missing/unknown provenance fields according to project policy;
- required credit not confirmed.

More advanced perceptual QC can wait.

## Export

A completed export should contain or reference:

```text
video.mp4
metadata sidecar (JSON and/or human-friendly text)
render manifest
QC result
```

User-facing metadata sidecar may include:

```text
title
description
hashtags
credits
source notes
```

Internal render manifest includes reproducibility details and source hashes.

## Local data layout

The application should default to a user data directory outside the Git repository.

Conceptual layout:

```text

  assets/
  thumbnails/
  proxies/
  cache/
  projects-or-manifests/
  exports/
```

The exact OS-specific default can be selected during implementation.

## CI

Because the repository is public, GitHub Actions can run the deterministic test suite.

CI should not require:

- NVIDIA GPU;
- production FFmpeg hardware encoders;
- live ChatGPT session;
- Qwen TTS model;
- internet source downloads;
- copyrighted fixtures.

Use fake providers and synthetic media. FFmpeg-dependent tests can use a software codec and small generated fixtures where the runner environment supports FFmpeg; otherwise capabilities should be feature-detected with explicit skips.

## Explicitly out of scope for v0.1

- automatic YouTube upload/scheduling;
- analytics dashboards;
- autonomous source scraping;
- full manga OCR pipeline;
- speaker attribution;
- Qwen TTS/voice cast;
- word-level forced alignment;
- long-form production;
- cloud multi-user deployment;
- distributed workers;
- a general-purpose NLE timeline UI;
- automatic legal/policy clearance.

## v0.1 acceptance criteria

v0.1 is accepted when:

1. The desktop service starts with one command documented for the target environment.
2. An Android phone on Wi-Fi can upload/share a source into the Inbox.
3. The source is hashed, stored, probed, and visible with a thumbnail/proxy.
4. A `hook_overlay` project can be prepared from that source.
5. Hook text can be entered manually; optional LLM suggestions work when configured.
6. A fast preview can be rendered and reviewed from the phone.
7. Final 1080x1920 output renders using NVENC on the target desktop when available and falls back cleanly elsewhere.
8. Basic QC runs and records pass/warnings/failures.
9. The MP4 and metadata/render manifest are exported.
10. At least the additional initial templates can be represented without adding new renderer architecture.
11. Batch/job state survives application restart.
12. No production source media or credentials need to live in the Git repository.

If these are true, Content Forge has crossed from an architecture exercise into a useful production system and is ready for voiced-content work.
